# ai-test-check

> **你的测试，是真的吗？**
>
> AI 写的测试经常"假绿"：100% 通过，但改坏代码还是绿。
> 这个工具用**变异测试**证明它——把代码改坏，看测试红不红。

---

## 📊 真实数据：我跑了 8 个开源项目

| 项目 | Star | 变异数 | 被杀 | 有效性 |
|---|---|---|---|---|
| browserify/events | 1.4k | 10 | 10 | **100%** |
| sindresorhus/slugify | 2.7k | 10 | 6 | **60%** |
| jonschlinkert/is-number | 286 | 10 | 2 | **20%** |
| browserify/sha.js | 298 | 10 | 0 | **0%** |
| crypto-browserify/createHash | 54 | 8 | 0 | **0%** |
| **chalk/chalk** | **23.3k** | 10 | 0 | **0%** |
| ljharb/object.assign | 106 | 10 | 0 | **0%** |
| browserify/parse-asn1 | 20 | 10 | 0 | **0%** |
| **平均** | | | | **≈23%** |

**最扎眼的**：`chalk`（2.3 万 star）有效性 **0%**，`events`（1.4k star）**100%**。

**同样 CI 全绿，差距从 0% 到 100%。**

> ⚠️ 诚实边界：只跑 8 个（不是 10 个），每仓库只随机抽 10 个变异。
> 「0%」不代表「测试完全没用」，只代表「这 10 个改动测试都没抓到」。

## 30 秒看懂

```
$ npx ai-test-check ./src

═══ AI 测试有效性检测 ═══
  ✅ 基线测试通过（可以开始变异）

  [1/5] calc.js  >= → >   ❌ 存活（测试没抓到）
  [2/5] calc.js  >= → >   ❌ 存活（测试没抓到）
  [3/5] calc.js  && → ||  ✅ 被杀（测试抓到了）
  [4/5] calc.js  >= → >   ❌ 存活（测试没抓到）
  [5/5] calc.js  === → !==  ✅ 被杀（测试抓到了）

═══ 结果 ═══
  变异总数: 5
  被杀: 2（测试抓到了）
  存活: 3（测试没抓到）

  ★ 测试有效性: 40%

  存活的变异（这些地方测试有洞）:
    calc.js:4  >= → >
    calc.js:8  >= → >
    calc.js:15  >= → >

  ❌ 测试有效性低（<50%）⇒ 测试可能是"假绿"，改坏代码也不会红
```

**一句话**：`40%` 意思是——你改坏 10 处代码，测试只能抓到 4 处。**剩下 6 处它看不见。**

## 为什么需要它

### AI 时代的新问题

AI 写代码，也写测试。但 AI 写的测试有个特征：

```js
// AI 常写的测试
test('isAdult works', () => {
  expect(isAdult(20)).toBe(true);   // ← 只测一个正常值
});
```

**问题**：如果源码是 `age >= 18`，改成 `age > 18`，这个测试**还是绿的**。
因为 20 岁在两种写法下都返回 true。

**你看到的**：✅ 测试全绿、✅ 覆盖率 100%、✅ CI 通过
**实际情况**：18 岁的人会拿到错误的答案，而没有任何测试能发现

### 现有工具不解决这个

| 工具 | 它回答的问题 | 它**不**回答的 |
|---|---|---|
| Jest / Vitest | 测试跑过了吗 | **测试有效吗** |
| Coverage | 代码被执行了吗 | **执行了但断言对吗** |
| ESLint | 代码风格对吗 | **逻辑对吗** |
| TypeScript | 类型对吗 | **运行时行为对吗** |

**变异测试是唯一能回答「测试有效吗」的方法。**

## 怎么用

### 安装

```bash
npm install -g ai-test-check
# 或
npx ai-test-check ./src
```

### 跑

```bash
# 最简
ai-test-check ./src

# 指定测试命令
ai-test-check ./src --test-cmd="npm test"

# 多变异一些（更准，但更慢）
ai-test-check ./src --max=30
```

### 输出到 CI

```yaml
# .github/workflows/test.yml
- name: Check test effectiveness
  run: npx ai-test-check ./src --max=20
```

**退出码**：`0` = 有效率 ≥50%；`1` = <50%（可用来卡 PR）

## 它怎么工作（原理）

```
1. 找到源码里的"可变异点"
   ===  !==  >  <  >=  <=  &&  ||

2. 逐个改坏
   age >= 18  →  age > 18

3. 跑测试
   测试变红 ⇒ "被杀" ⇒ 测试有效 ✅
   测试还绿 ⇒ "存活" ⇒ 测试有洞 ❌

4. 恢复源码（每轮都恢复，不留残留）

5. 报告
   有效性 = 被杀数 / 总数
```

## 诚实边界（MVP 限制）

| 限制 | 说明 |
|---|---|
| **只支持 JS/CJS** | 不做 AST，纯文本替换 |
| **只变异 6 类** | `===` `!==` `>` `<` `>=` `<=` `&&` `\|\|` |
| **一次一处** | 慢但准（10 处约 10-30 秒） |
| **可能误判** | 变异造出语法错误时，被当成"被杀"（方向保守，**会高估**有效性） |
| **不测边界值** | 不生成新输入，只改代码 |
| **需要基线全绿** | 测试本来就是红的，测不出有效性 |

**★ 最重要的一条**：这个工具**不能证明你的测试完美**，只能证明**你的测试有洞**。

---

## 和「覆盖率」的区别

```
覆盖率 100% + 有效性 40%
  ⇒ 每行代码都跑了，但一半的改动测试看不见
  ⇒ 这是"假绿"

覆盖率 60% + 有效性 90%
  ⇒ 有些代码没测，但测了的部分是真的
  ⇒ 这比上面健康
```

**覆盖率说「测了没」，变异测试说「测得住吗」。**

## 灵感来源

- **mewt**（Rust 变异测试）—— 「测试的有效性，而不是测试的存在」
- **Stryker**（JS 变异测试框架）—— 工业级实现
- **PIT**（Java 变异测试）—— 最成熟的实现

本工具是**简化版**：不做 AST、不做并行、不支持多语言。目标不是替代它们，是**让"测试有效性"这个概念能被 30 秒理解**。
