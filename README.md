# ai-test-check

> **你的测试，是真的吗？**
>
> AI 写的测试经常「假绿」：100% 通过，但改坏代码还是绿。
> 这个工具用**变异测试**证明它 —— 把代码改坏，看测试红不红。

```bash
npx ai-test-check ./src
```

**30 秒后你会知道**：你改坏 10 处代码，测试能抓到几处。

---

## 30 秒看懂

```
$ npx ai-test-check ./src

═══ AI 测试有效性检测 ═══
  ✅ 基线测试通过（可以开始变异）

  [1/5] calc.js  >= → >     ❌ 存活（测试没抓到）
  [2/5] calc.js  >= → >     ❌ 存活（测试没抓到）
  [3/5] calc.js  && → ||    ✅ 被杀（测试抓到了）
  [4/5] calc.js  >= → >     ❌ 存活（测试没抓到）
  [5/5] calc.js  === → !==  ✅ 被杀（测试抓到了）

═══ 结果 ═══
  变异总数: 5
  被杀: 2（测试抓到了）
  存活: 3（测试没抓到）

  ★ 测试有效性: 40%

  存活的变异（这些地方测试有洞）:
    calc.js:4   >= → >
    calc.js:8   >= → >
    calc.js:15  >= → >
```

**`40%` 意思是**：你改坏 10 处代码，测试只能抓到 4 处。**剩下 6 处它看不见。**

## 5 分钟上手

### 1. 跑

```bash
# 不用安装，直接跑
npx ai-test-check ./src

# 或全局安装
npm install -g ai-test-check
ai-test-check ./src
```

### 2. 参数

```bash
ai-test-check ./src --max=20          # 最多变异 20 处（更准，但更慢）
ai-test-check ./src --all             # 跑所有变异点（结果稳定，但慢）
ai-test-check ./src --test-cmd="npm test"  # 指定测试命令
ai-test-check ./src --file="src/*.js"      # 只测某些文件
```

### 3. 看结果

| 有效性 | 判断 | 该做什么 |
|---|---|---|
| **≥80%** | ✅ 可信 | 保持 |
| **50-79%** | ⚠ 中等 | 补边界测试 |
| **<50%** | ❌ 有洞 | 系统性补测试 |

### 4. 常见报错

| 报错 | 原因 | 解决 |
|---|---|---|
| `❌ 基线测试就是红的` | 你的测试本来就失败 | 先让测试全绿 |
| `❌ 找不到测试命令` | 没有 `scripts.test` | 用 `--test-cmd="<你的命令>"` |
| `⚠ N 个文件解析失败` | 有些文件是 ES5/TS | 正常，跳过（会报告） |
| `可变异点: 0 个` | 源码里没有运算符 | 换一个有逻辑的目录 |

## 🧪 真实例子：5 个测试全绿，但有效性只有 14%

`examples/calculator/` 里有一个**故意写弱**的测试项目：

```bash
cd examples/calculator
node test.js
# ✅ 5 个测试全部通过

npx ai-test-check .
# ★ 测试有效性: 14%
```

**测试全绿，但改坏代码不会红。**

### 它报出的分组

```
存活的变异按类型分组:

  边界条件（4 处）⇒ 补「等于/不等于」的情况
    calc.js:40  >= → >
    calc.js:32  >= → >
    calc.js:21  >= → >

  数字边界（3 处）⇒ 补「刚好等于/差一」的情况
    calc.js:32  数字边界
    calc.js:40  数字边界
    calc.js:21  数字边界

  逻辑组合（2 处）⇒ 补「只满足一个条件」的情况
    calc.js:40  && → ||
    calc.js:32  && → ||
```

**★ 这比「有效性 25%」有用得多** —— 它直接告诉你「该补哪类测试」。

### 它漏了什么

| 源码 | 测试 | 洞 |
|---|---|---|
| `discount(100)` 返回 90 | 只测了 `discount(200)` | **边界 100 没测** |
| `canVote(18, true)` 返回 true | 只测了 `canVote(20, true)` | **边界 18 没测** |
| `canVote(20, false)` 返回 false | 没测 | **非公民组合没测** |
| `isWeekday(1)` / `isWeekday(5)` | 只测了 3 | **边界 1 和 5 没测** |
| `isWeekday(0)` / `isWeekday(6)` | 没测 | **周末没测** |

### 修复后

给每个边界加测试，有效性从 **14% → 80%+**。

**★ 这就是「覆盖率 100% 但测试无效」的具体样子。**

## 为什么需要它

### AI 时代的新问题

AI 写代码，也写测试。但 AI 写的测试有个特征：

```js
// AI 常写的测试
test('isAdult works', () => {
  expect(isAdult(20)).toBe(true);   // ← 只测一个正常值
});
```

**问题**：如果源码是 `age >= 18`，改成 `age > 18`，这个测试**还是绿的**。
因为 20 岁在两种写法下都返回 true。

**你看到的**：✅ 测试全绿、✅ 覆盖率 100%、✅ CI 通过
**实际情况**：18 岁的人会拿到错误的答案，而没有任何测试能发现

### 现有工具不解决这个

| 工具 | 它回答的问题 | 它**不**回答的 |
|---|---|---|
| Jest / Vitest | 测试跑过了吗 | **测试有效吗** |
| Coverage | 代码被执行了吗 | **执行了但断言对吗** |
| ESLint | 代码风格对吗 | **逻辑对吗** |
| TypeScript | 类型对吗 | **运行时行为对吗** |

**变异测试是唯一能回答「测试有效吗」的方法。**

### 为什么 AI 写的测试特别容易这样

**根本原因**：AI 代码和 AI 测试共享同样的误解。

```
AI 写代码时理解错了需求
AI 写测试时用了同样的错误理解
⇒ 测试「验证」了错误行为
⇒ 全绿，但代码是错的
```

有个 HN 用户的原话：

> 「For 100% of the root cause analyses for critical production defects that I've done over the past 18 months or so, a key finding was that AI-generated tests asserted that the defective behavior was correct.」
>
> —— [Hacker News](https://news.ycombinator.com/item?id=49711610) 2026-09-15

## 它怎么工作（原理）

```
1. 用 acorn 解析成 AST，找真正的变异点
   · 运算符：=== !== > < >= <= && ||
   · 布尔字面量：true ↔ false
   · 数字边界：18 → 19（探测边界测试）
   · 状态字符串：'active' ↔ 'inactive'
   ★ 正则/字符串/注释里的符号不会被误判

2. 逐个改坏
   age >= 18  →  age > 18

3. 跑测试
   测试变红 ⇒ "被杀" ⇒ 测试有效 ✅
   测试还绿 ⇒ "存活" ⇒ 测试有洞 ❌

4. 恢复源码（每轮都恢复，不留残留）

5. 报告
   有效性 = 被杀数 / 总数
```

## 为什么用 AST（v0.2.0 的关键改动）

### 旧版的问题

旧版用正则找变异点：

```js
// 旧版逻辑
{ name: '>= → >', re: /(?<![<>=!])>=(?!=)/g, to: '>' }
```

**问题**：它会把正则字面量里的符号当成运算符。

```js
const RE = /(?<![<>=!])>=(?!=)/g;
//                    ↑ 这个 (?!=) 被当成「!= 比较」
const MSG = "a >= b && c !== d";
//             ↑ 字符串里的符号也被当成运算符
```

### 实测对比（2026-10-23）

同一份代码（含注释、正则、字符串、5 个真运算符）：

| 版本 | 找到变异点 | 准确率 |
|---|---|---|
| **旧版（正则）** | **14 个** | 5/14 = **36%**（9 个是假符号） |
| **新版（AST）** | **5 个** | 5/5 = **100%** |

### 新版怎么做的

```js
const acorn = require('acorn');
const ast = acorn.parse(code, { ecmaVersion: 2022 });

// 只认 AST 里的运算符节点
if (node.type === 'BinaryExpression') {
  ops.push({ op: node.operator, start: node.left.end, end: node.right.start });
}
```

**为什么 AST 准确**：

- 正则字面量 ⇒ `Literal` 节点，不是运算符
- 字符串 ⇒ `Literal` 节点，不是运算符
- 注释 ⇒ **不在 AST 里**（解析时丢弃）

### 代价

- 多一个依赖：`acorn`（8.19.0，**零传递依赖**，约 20KB）
- 解析失败的文件会跳过（会报告，不静默）

## 开发

```bash
# 跑自检（10 条，验证 AST 变异器 + 分类函数）
node bin/ai-test-check.cjs --selftest

# 或
npm test
```

**★ 自检覆盖什么**：
- AST 能找到真运算符
- 正则/字符串里的符号不算
- 布尔/数字/状态字符串能变异
- 语法错误不崩
- 0 和 1 不参与数字变异（避免噪音）

**★ 不覆盖什么**：
- 完整的变异测试流程（要真项目才能测）
- 跨文件行为

## 诚实边界（MVP 限制）

| 限制 | 说明 |
|---|---|
| **只支持 JS/CJS** | 用 acorn 做 AST（ES2022），不做 TS/Python |
| **变异类型** | 运算符（8 种）+ 布尔字面量 + 数字边界 + 状态字符串 |
| **不改** | 条件取反（`if (x)` → `if (!x)`）、返回值类型 |
| **一次一处** | 慢但准（10 处约 10-30 秒） |
| **可能误判** | 变异造出语法错误时，被当成"被杀"（方向保守，**会高估**有效性） |
| **不测边界值** | 不生成新输入，只改代码 |
| **需要基线全绿** | 测试本来就是红的，测不出有效性 |
| **抽样波动** | 默认只抽 10 个；用 `--all` 跑全量才稳定 |
| **单文件** | 无跨文件/模块间契约检测 |

**★ 最重要的一条**：这个工具**不能证明你的测试完美**，只能证明**你的测试有洞**。

## 和「覆盖率」的区别

```
覆盖率 100% + 有效性 40%
  ⇒ 每行代码都跑了，但一半的改动测试看不见
  ⇒ 这是"假绿"

覆盖率 60% + 有效性 90%
  ⇒ 有些代码没测，但测了的部分是真的
  ⇒ 这比上面健康
```

**覆盖率说「测了没」，变异测试说「测得住吗」。**

## 灵感来源

- **mewt**（Rust 变异测试）—— 「测试的有效性，而不是测试的存在」
- **Stryker**（JS 变异测试框架）—— 工业级实现
- **PIT**（Java 变异测试）—— 最成熟的实现

本工具是**简化版**：不做并行、不支持多语言。目标不是替代它们，是**让"测试有效性"这个概念能被 30 秒理解**。
